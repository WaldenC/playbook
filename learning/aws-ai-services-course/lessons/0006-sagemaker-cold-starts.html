Lesson 0006 · Cold starts

Why your first request crawls

A serverless SageMaker endpoint scales to zero when idle, and the first request that wakes it pays the full startup bill: usually 6–45 seconds. The bill is the cold start — the #1 daily problem for the software development engineers (SDEs) who run SageMaker inference.

The scale-to-zero bargain

Serverless inference scales to zero: with no traffic, the endpoint holds zero running containers. The first call triggers a full bring-up, and the caller waits through it — typically 6–45 s.

That wait is the platform's own doing: idle means zero cost, but the wake-up is not free. The SDE's job is deciding which of the three fixes below pays for the traffic shape.

Four stages, one bill

A cold call runs a four-stage chain. The container boots, pulls its image — 10 GB and up, over the network — loads the model weights into GPU memory, and only then emits the first token. For Llama-3.1-70B, the weight load alone runs ~400 s.

Each fix AWS built targets one stage rather than the whole chain, so diagnosis comes first: is the wait in the pull, in the weights, or everywhere?

Three fixes, three targets

Three remedies exist, each aimed at a different stage.

Provisioned concurrency — skip the whole chain

Provisioned concurrency keeps warmed copies of the endpoint running ahead of time, so a request lands on a live container and never touches the chain. You pay for those copies whether or not a request arrives, and the cap is 200 concurrent invocations.

Container image caching — kill the re-pull

Since June 2026, SageMaker AI caches container images on the host, so a scaling event pulls once instead of re-downloading 10 GB+ per instance. End-to-end scale-out runs up to 2x faster.

Fast Model Loader — stream the weights

Fast Model Loader (2024) pre-shards weights into 8 MB chunks and streams them from S3 straight into GPU memory. DMA — direct memory access — lets the accelerator pull bytes straight into its own memory: no disk, no CPU staging. Chunked streaming means the first weights land in memory while the rest are still in flight. Loading runs up to 15x faster: Llama-3.1-70B scale-out drops from ~407 s to ~335 s, and autoscaling is ~58% faster.

Sources: Fast Model Loader (AWS ML blog, 2024) · container image caching (AWS what's new, June 2026).

The three fixes compose. Provisioned concurrency means you never cold start at all; when you do, image caching and Fast Model Loader shorten the two heaviest stages. Boot has no fix — that is why warm copies exist.

Which fix, which stage?

An endpoint scales to zero and steady customers eat a 30 s first call. Which fix makes requests skip the whole chain?

Provisioned concurrency keeps warmed copies running, so a request lands on a live container and never boots, pulls, or loads. The trade: you pay for those copies whether or not a request arrives, and the cap is 200 concurrent invocations.

Container image caching attacks which stage of the cold start?

Image caching lives on the host, so a fresh instance reads the image locally instead of re-pulling 10 GB+ from the registry. Since June 2026 it runs end-to-end scale-out up to 2x faster.

Fast Model Loader attacks which stage of the cold start?

Fast Model Loader pre-shards weights into 8 MB chunks and streams them S3 → GPU memory via DMA, bypassing disk — up to 15x faster loading. Llama-3.1-70B scale-out drops from ~407 s to ~335 s, and autoscaling is ~58% faster.

What does Fast Model Loader do differently from the other two fixes?

The distinguishing move is the shards: weights are cut into 8 MB chunks and streamed straight from S3 into GPU memory, so the model never lands on local disk. Warm copies and image caching attack the same cold start from other stages.
